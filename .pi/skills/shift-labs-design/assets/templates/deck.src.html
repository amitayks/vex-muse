Sensor patterns

Agents write small programs, called sensors, that check a system on a timer and wake the agent when something needs attention. We read every sensor we could find and sorted them into eight patterns. This deck shows each pattern with real examples and a code sketch.

Each tick is one run of a sensor’s code. Orange runs found something and fired.

The basics

What a sensor is

Schedules fire on the clock, people chat, and sensors trigger on change. A sensor is a few lines of code the agent writes for itself. The platform runs it every few seconds up to once a day.

61%of sensors run every five minutes or more often. 22% run every minute.

71%of the agent turns that sensors start end with nothing to do.

44%of those turns happen outside office hours or at the weekend.

A run is one execution of the sensor’s code. A turn is the agent’s work after a sensor fires. Turn outcomes come from the Agent Work Index task codes. Each organization counts equally, and codes seen at too few organizations are not shown.

Pattern 1 of 8

New items

The most common pattern. The sensor reads a list and fires once for each item it has not seen before.

An inbox

Keep a cursor and fire only for items after it. On the first run, set the cursor without firing.

45%of sensors fire on new items

Examples
  1. Photos from kitchen stations. Each station posts goods-received notes in its own chat group. One sensor per group sends new photos to the agent that records them.
  2. Invoice requests. Guest messages asking for an invoice go to the agent that handles accounting.
  3. Comments on a shared sheet. A new comment wakes the assistant that maintains the sheet.
  4. Merged pull requests. Everything merged since the last run goes into one hourly summary.
if (!cursor) return { newCursor: Date.now(), events: [] }  // first run

const fresh = await inbox.list({ since: cursor })
return {
  newCursor: fresh.at(-1)?.receivedAt ?? cursor,
  events: fresh.map(m => ({
    id: m.id,                                   // dedup key
    prompt: `New mail from ${m.from}: ${m.subject}`,
  })),
}

Pattern 2 of 8

No reply in time

The sensor fires when an expected reply or update has not arrived within a set time.

A guest message with no reply Five reminders

Before each reminder it checks the thread again and stops if staff have replied. Each reminder has its own id, so it fires once.

Check the thread again before each reminder, and send each reminder only once.

4%of sensors fire when a reply is overdue

Examples
  1. Unanswered guest messages. Reminders at 5, 15, 35, 75 and 155 minutes until someone replies in the booking inbox.
  2. Reception chat. A minute after a guest writes, the sensor checks whether staff replied. If nobody did, it asks the agent to reply.
  3. An email question. Someone was asked by email for visit times. The sensor fires if they have not answered.
  4. Overnight emergencies. An emergency reported between 02:00 and 07:00 wakes a person as well as the agent.
const REMINDERS = [5, 15, 35, 75, 155]          // minutes
const events = []
for (const t of await guestInbox.threads()) {
  if (t.lastFrom !== 'guest') continue          // staff replied
  const waited = minutesSince(t.lastAt)
  const n = REMINDERS.filter(m => waited >= m).length
  if (n) events.push({
    id: `${t.id}:${n}`,                         // one fire per reminder
    prompt: `Guest waiting ${waited} min (reminder ${n}/5)`,
  })
}
return { events }

Pattern 3 of 8

A state changed

The sensor fires when something it already tracks is in a different state from the last run.

The sensor saves the fields it cares about as one string. If the string is the same as last time, it does not fire.

Save the fields you care about as one string, and fire when the string changes.

10%of sensors fire on a change

Examples
  1. A flight. The status, gate or landing time changed. The agent tells the person waiting.
  2. A deployment. A server is running a new build, so the agent checks what shipped.
  3. A bank account. The balance changed or new transactions appeared.
  4. A map. The list of buildings in an area changed, so the agent updates the map.
const f = await flights.status({ number, date })
const print = [f.status, f.gate, f.eta].join('|')
if (print === cursor) return { events: [] }       // unchanged

return {
  newCursor: print,
  events: [{
    id: print,
    prompt: `Flight ${number}: ${f.status}, gate ${f.gate}, lands ${f.eta}`,
  }],
}

Pattern 4 of 8

Two systems disagree

The sensor compares two systems that should agree and fires once for each record where they do not.

Rooms that match do not fire. Each room that does not match fires once.

Read both systems in the sensor and fire once per record that does not match.

4%of sensors compare two systems

Examples
  1. Arrivals and cleaning. A last-minute booking is for a room with no cleaning scheduled.
  2. Guest requests and housekeeping. A guest asked for a sofa bed or a crib, and it is missing from the housekeeping plan.
  3. A closed deal. The CRM marks a deal as won, but its folder is missing required documents.
  4. A transcription. The transcription finished but was never logged in the tracking sheet.
const arrivals = await bookings.arrivals({ day })
const planned = new Set(
  (await housekeeping.plan({ day })).map(c => c.room))

return {
  events: arrivals
    .filter(a => !planned.has(a.room))          // no cleaning planned
    .map(a => ({
      id: `${day}:${a.room}`,
      prompt: `Room ${a.room} has an arrival but no cleaning`,
    })),
}

Pattern 5 of 8

A deadline is near

The sensor fires at set points before a due date.

Reminders before a due date

Each reminder’s id is the item plus the number of days, so each reminder fires once.

Pick the reminder points in advance, and give each one its own id so it fires once.

2%of sensors watch a deadline

Examples
  1. Leases. Office leases ending within twelve months are flagged for the broker.
  2. A money transfer. Reminders 14, 7, 3 and 1 days before the due date, then an overdue notice.
  3. Policy reviews. Security policies due for review are flagged six weeks ahead.
  4. Onboarding. Overdue checklist items for a new hire.
const DAYS_BEFORE = [14, 7, 3, 1, 0]
const events = []
for (const d of await crm.openTransfers()) {
  const left = daysUntil(d.dueDate)
  const mark = DAYS_BEFORE.find(m => left <= m)
  if (mark === undefined) continue
  events.push({
    id: `${d.id}:${mark}`,                      // one fire per reminder
    prompt: left < 0 ? `Overdue: ${d.name}` : `${left} days left: ${d.name}`,
  })
}
return { events }

Pattern 6 of 8

A number out of range

The sensor checks a number against a range. It fires when the number leaves the range and again when it comes back.

A value with a normal range

It fires when the value leaves the range and once when it comes back. It does not fire on every run in between.

Save the last level in the cursor, and fire only when the level changes.

6%of sensors watch a number

Examples
  1. Daily spend. The day’s AI spend goes over a set amount.
  2. A server. Disk, memory and CPU have warning and critical levels, with a message when they return to normal.
  3. A trading position. The price approaches the level at which the position would be closed.
  4. Records behind a report. Records changed too much since the report’s snapshot. It fires at most once a day.
const disk = (await host.stats()).diskPct
const level = disk >= 83 ? 'critical' : disk >= 78 ? 'warning' : 'ok'
if (level === cursor?.level) return { events: [] }

return {
  newCursor: { level },
  events: [{
    id: `${level}@${hourKey()}`,
    prompt: level === 'ok' ? `Disk back to ${disk}%` : `Disk ${level}: ${disk}%`,
  }],
}

Pattern 7 of 8

A set time

About one sensor in six reads only the time. It works like a schedule that remembers whether it has already run.

Reads only the time

The cursor records that today’s run happened. A one-time reminder deletes itself after it fires.

Record in the cursor that the run happened. Make one-time reminders one-shot so they delete themselves.

22%of sensors fire at a set time

Examples
  1. Personal reminders. A reminder at a set date and time, deleted once it is sent.
  2. Morning jobs. A housekeeping pass each morning that wakes the agent only if something needs a decision.
  3. A nightly refresh. A map of open tasks rebuilt once a day at midnight.
  4. A morning plan check. Every few minutes, a check that today’s plan was sent on time.
const due = Date.parse('2026-09-12T06:40:00+03:00')
if (cursor?.sent || Date.now() < due) return { events: [] }

await messages.send({ to: me, text: 'Take the running shoes' })
return { newCursor: { sent: true }, events: [] }
// one-shot: the runtime deletes it after it fires

Pattern 8 of 8

Something is down

The sensor checks that a service, connection, login or agent is working, and fires when it is not.

Probe a service every minute

It alerts after two failures in a row and sends one message when the service is back. The failure count is kept in the cursor.

Alert after two failures in a row, send one message on recovery, and keep the failure count in the cursor.

7%of sensors check that something is working

Examples
  1. A website. Checked every minute. It alerts after two failed checks in a row and again when the site is back.
  2. Connections. A network link and a WhatsApp sync are restarted when they drop.
  3. A shared model account. Several agents run on one account. If it disconnects they all fail, so a sensor checks it.
  4. Lost runs. Runs that stopped before doing anything are found and restarted.
const ok = await probe(url, { timeoutMs: 12_000 })
const fails = ok ? 0 : (cursor?.fails ?? 0) + 1
const down = fails >= 2 || (cursor?.down && !ok)
const events = []
if (fails === 2)
  events.push({ id: `down@${Date.now()}`, prompt: `${url} is down` })
if (ok && cursor?.down)
  events.push({ id: `up@${Date.now()}`, prompt: `${url} recovered` })
return { newCursor: { fails, down }, events }

Techniques · 1

Avoiding duplicate and unwanted fires

Agents at different organizations, with no shared code, arrived at the same four techniques.

Set a baseline first

On its first run the sensor records the current state and fires nothing, so old items are not reported.

if (!cursor)
  return { newCursor: now(), events: [] }

Give each event an id

The id combines the item and the step, such as a thread and a reminder number. The platform drops ids it has already fired.

t42:1  fired
t42:1  dropped
t42:2  fired
t42:2  dropped
t42:3  fired
{ id: `${thread}:${step}`, prompt }

Wait for a second failure

A single failed check does not alert. The sensor alerts on the second failure in a row and sends one message when things recover.

fails = ok ? 0 : fails + 1
if (fails === 2) alert()
if (ok && wasDown) recovered()

Hold alerts overnight

Routine alerts that come in overnight are held and sent together in the morning. Urgent ones go out immediately.

if (night() && !urgent)
  return { newCursor: queue(e), events: [] }
